# Saved-branch selection diagnostic, after the strict Cycle-22 gate

Recorded 2026-09-16. This is an offline analysis of existing native branches,
not a new native experiment, learned-policy admission or restart of Cycle 23.
Both the programs and outcomes are already known. All policies below are
human-written post-hoc controls; do not describe their scores as held-out results.

## Question and fixed scope

Is there any quality headroom for learned activation on the repair alternatives
already represented by the fourteen-record static/manual-control experiment?

Use its ten Cycle-13 edited actions and the one Cycle-18B edited action. Pair
each with the factual control at the identical checkpoint (rows 10, 11 or 12).
Retain all eleven pairs, including harmful and ineffective edits. Verify the
entire worker request differs only at the one target action; independently
compare saved pre-action states using the existing checker. Never execute code,
read hidden values as policy features or rerun a native scorer.

For denominator transparency, also inventory the existing Cycle-17B and Cycle-18B
effect reports. These add thirty edit records outside this eleven-pair slice;
they are not silently treated as evaluated by the fourteen-record control.
Do not synthesize missing public context or broaden the coverage query.

## Controls

Use only saved B warnings and public-only manual findings for the original and
edited programs. The policy function receives no IDs, outcomes or execution logs.

1. No-op: keep the original branch.
2. Always-edit: select the supplied edited branch.
3. Manual all-clear: edit only if the original warns and the edited branch has
   no detected risk under B plus the full manual control.
4. Manual risk reduction: edit only if the edited program strictly reduces the
   set of known name/pagination/consumer warning reasons, introduces no new
   reason and has no unknown pagination status. Otherwise keep the original.
   This permits a useful partial repair; complete warning elimination is not
   required. It is an explicitly human-written activation policy.
5. Quality oracle: choose a successful branch if one exists. Ties retain the
   original. It uses outcome labels and is an unattainable ceiling, not a method.

All controls select between the SAME existing pair of branches; none generates
a new edit or changes future actions. Unknown findings abstain. A strict subset
of warning reasons is not a sound semantic improvement proof; measure its saved
effects instead of declaring it correct by construction.

Report every selection and resulting native outcome; successes, beneficial and
harmful flips relative to no-op; remaining oracle quality headroom; scenario and
checkpoint multiplicity; and saved native API-log counts. API-log entries are a
cost proxy, not model calls or USD. Report missing cost data rather than invent it.
The common candidate/inspection budget is logically shared; archived donor
acquisition cost and unmeasured inspection latency remain unknown. No causal
claim about induction or authoring effort can follow from policy recombination.

If the manual risk-reduction rule reaches the quality oracle, learned selection
cannot have a positive quality increment on these same fixed pairs. This only
rules out their use as an informative quality-superiority test. It does not rule
out better repair generation, different checkpoints, cost benefits, new tasks,
or every possible learned contract. No scaling or paid proposal follows merely
from a passing local implementation.
