# Cycle 18A: public-code donor input binding and target output closure

Registered 2026-09-16 after the complete cycle-17 result and failure audit, before

## Hypothesis and competing explanations

The all-boundary transplants fail partly because donor input names differ from
target names and the removed target span contains setup or outputs needed by the
unchanged consumer. A generic mapping inferred from corresponding public API-call
keyword arguments may remove these immediate construction defects. Shared names
or API signatures do not prove semantic equivalence; stale continuations, multiple
task defects, wrong API fields and misleading anchors may still defeat all effects.

The minimal new operator is a bounded supplement to the unchanged old proposal:

1. Inspect corresponding literal API paths rooted at `apis` in original target
   and donor code. Match keyword names on the same full API path. For external
   donor identifiers used as keyword values, infer only a unique, consistent
   target identifier mapping. Do not use a task-ID table, API-name-specific rule,
   guessed credential constant, hidden namespace value or model-written patch.
2. Do not rename a donor-local loop/output binding through this input mapping.
   Keep rejected, conflicting, ambiguous or unsupported cases explicitly.
3. If a required mapped target input's original setup assignment is inside the
   removed span, retain that target-authored setup when a restricted syntax check
   supports it (start with literal constant assignments). Do not copy a donor's
   task-specific authentication value or silently assume an unbound name exists.
4. Check obvious output closure: bindings produced by the removed original span
   and consumed by untouched statements must remain available through the new
   block or preserved target setup/prefix. Reject unmatched required outputs;
   do not insert empty placeholder outputs to make the code merely run.
5. Preserve AST identity of untouched target prefix/suffix. Record exact mappings,
   retained setup, code/AST digests, uncertainty and every rejection. These are
   deliberately bounded syntax checks, not a sound analysis of arbitrary Python
   aliasing, mutation, dispatch, conditional definitions or side effects.

Any necessary departure from this restricted operator must be recorded in a new
dated amendment before the broader construction is applied to the build corpus.
No name substitution may be manually selected because a native result looks good.
